# امضای نسخهٔ نهایی — راهنمای فارسی

نسخه‌های 0.4.0 و 0.5.0 با **امضای debug** منتشر شده‌اند. برای نصب و استفادهٔ شخصی
کافی است، اما برای انتشار در Google Play یا تحویل به کاربران دیگر مناسب نیست.
این راهنما توضیح می‌دهد چطور امضای واقعی بسازید.

---

## چرا این کار را باید خودتان انجام دهید

کلید امضا **هویت دائمی** برنامهٔ شماست:

- اندروید اجازهٔ نصب یک به‌روزرسانی را فقط وقتی می‌دهد که با **همان کلید** امضا شده باشد.
  اگر کلید را گم کنید، کاربران باید برنامه را حذف کنند (و دادهٔ محلی‌شان از بین می‌رود)
  تا بتوانند نسخهٔ جدید را نصب کنند.
- اگر کلید لو برود، هر کسی می‌تواند یک «به‌روزرسانی» جعلی با هویت شما منتشر کند.

به همین دلیل کلید هیچ‌وقت در مخزن، در CI، یا در گفتگو قرار نمی‌گیرد.

---

## ۱. ساخت کلید

روی **کامپیوتر خودتان** (نه در GitHub Actions):

```bash
cd DuoLink
./scripts/make-release-keystore.sh
```

اسکریپت این کارها را انجام می‌دهد:

1. یک کلید RSA ۴۰۹۶ بیتی با اعتبار ۱۰٬۰۰۰ روز (≈۲۷ سال) می‌سازد
2. یک رمز قوی تصادفی تولید و چاپ می‌کند
3. فایل `keystore/duolink-release.jks` و فایل `keystore.properties` را می‌سازد
4. **کلید را باز می‌کند و تأیید می‌کند** که واقعاً قابل استفاده است (کلید خراب بدتر از
   کلید نداشتن است، چون بعداً با خطای گمراه‌کننده ظاهر می‌شود)

خروجی نمونه:

```
  keystore      : keystore/duolink-release.jks
  properties    : keystore.properties
  alias         : duolink
  certificate   : SHA256 56:BA:79:...
  keystore hash : 82f9331b7f4a479e8a3f8204267976708cdf205e31f7297ecce0ef4d2e9d8287
```

> **رمز را همین حالا در یک password manager ذخیره کنید.** اسکریپت فقط یک بار
> چاپش می‌کند و در هیچ فایلی خارج از `keystore.properties` نگه نمی‌دارد.

---

## ۲. پشتیبان‌گیری (این مرحله را رد نکنید)

سه چیز را، **جدا از این کامپیوتر**، در جایی امن نگه دارید:

1. `keystore/duolink-release.jks`
2. `keystore.properties` (شامل رمز)
3. رمز، در password manager

اگر هر دو نسخه فقط روی یک دیسک باشند، یک خرابی دیسک توانایی انتشار به‌روزرسانی را
برای همیشه از بین می‌برد.

---

## ۳. ساخت نسخهٔ امضاشده

```bash
cd DuoLink
./gradlew assembleRelease
```

اگر `keystore.properties` پیدا نشود، بیلد این هشدار را چاپ می‌کند:

```
DuoLink: keystore.properties not found - the release APK will carry the DEBUG signature.
```

**اگر این هشدار را نمی‌بینید، یعنی APK با کلید خودتان امضا شده است.** این رفتار عمدی
است: CI هیچ keystore ندارد و اگر بیلد بدون کلید شکست بخورد، کل خط لولهٔ تست از کار
می‌افتد. در عوض، بیلد هرگز بی‌سروصدا ادعا نمی‌کند امضای release دارد.

---

## ۴. تأیید امضا

```bash
$ANDROID_HOME/build-tools/35.0.0/apksigner verify --print-certs \
    app/build/outputs/apk/release/app-release.apk
```

باید `certificate DN: CN=DuoLink` را ببینید و **نه** `CN=Android Debug`.

مقایسهٔ اثر انگشت گواهی با آنچه اسکریپت چاپ کرد، تأیید نهایی است.

---

## ۵. تفاوت با نسخهٔ منتشرشدهٔ فعلی

| | v0.5.0 (فعلی) | نسخهٔ امضاشدهٔ شما |
|---|---|---|
| امضا | debug | کلید شما |
| قابل نصب | ✅ | ✅ |
| به‌روزرسانی روی نسخهٔ قبلی | ✅ (همان امضای debug) | ❌ **نه** — باید اول حذف شود |
| مناسب Play Store | ❌ | ✅ |

> **نکتهٔ مهاجرت:** چون امضای debug با امضای شما متفاوت است، اندروید اجازهٔ
> به‌روزرسانی مستقیم روی v0.5.0 نمی‌دهد. باید یک بار برنامه را حذف کنید و نسخهٔ جدید
> را نصب کنید. دادهٔ محلی (گفتگوها، کلیدها، اعتماد) پاک می‌شود و باید دوباره
> جفت‌سازی کنید. **این را قبل از حذف بدانید.**

---

## ۶. امضا در CI (اختیاری)

اگر می‌خواهید GitHub Actions هم نسخهٔ امضاشده بسازد، سه راز را در
`Settings → Secrets and variables → Actions` بسازید:

| نام راز | مقدار |
|---|---|
| `DUOLINK_KEYSTORE_BASE64` | خروجی `base64 -w0 keystore/duolink-release.jks` |
| `DUOLINK_KEYSTORE_PASSWORD` | رمز keystore |
| `DUOLINK_KEY_ALIAS` | `duolink` |

> **هشدار:** اگر مخزن عمومی است، هر کسی با دسترسی به Actionها می‌تواند رازها را
> استخراج کند. همچنین workflowهای pull request از forkها به رازها دسترسی ندارند.
> برای اکثر پروژه‌ها، ساختن نسخهٔ امضاشده روی کامپیوتر خودتان ساده‌تر و امن‌تر است.

---

## اگر کلید را گم کردید

راهی برای بازیابی نیست. گزینه‌ها:

1. **Play Store:** اگر از *Play App Signing* استفاده می‌کنید، گوگل کلید امضای نهایی را
   نگه می‌دارد و می‌توانید کلید آپلود را از طریق پشتیبانی بازنشانی کنید. این یکی از
   دلایل مهم استفاده از Play App Signing است.
2. **بدون Play:** باید بستهٔ جدیدی با `applicationId` متفاوت منتشر کنید، یا از کاربران
   بخواهید حذف و نصب مجدد کنند.

این دقیقاً همان چیزی است که مرحلهٔ ۲ (پشتیبان‌گیری) برای جلوگیری از آن وجود دارد.
